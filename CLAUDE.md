# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Wunderland is a native Symbian (Anna / Belle) client for the [Wunderland Store](https://github.com/WunderWungiel/Wunderland-Store). It is a rebranded fork of schumi1331's AppList client, so comments and some identifiers still say "AppList". Stack: Qt 4.7/4.8 + QtQuick 1.1 + Symbian Qt Components (`com.nokia.symbian 1.1`) + Qt Mobility (feedback, systeminfo, publishsubscribe), plus native Symbian C++ APIs.

## Building

There is no test suite or linter. The app is built with the Symbian Qt SDK (Qt 4.7.4, `C:\QtSDK\Symbian\SDKs\Symbian3Qt474`). Build with `build_symbian.bat [release|debug]` (qmake → `make release-gcce` → `make sis`, in-source); it produces an unsigned `Wunderland.sis`. Generated files (`Makefile`, `*.mmp`, `*.pkg`, `bld.inf`, `moc_*.cpp`, `qrc_*.cpp`) are gitignored.

- Desktop build (for quick checks of the C++ backend): a shadow build with the SDK's desktop Qt, e.g. `C:\QtSDK\Desktop\Qt\4.8.1\mingw\bin\qmake -spec win32-g++` then `mingw32-make release` (with `C:\QtSDK\mingw\bin` on `PATH`). Never run it in-source: it would overwrite the Symbian `Makefile`. It compiles and starts, but the QML needs `com.nokia.symbian` and doesn't load. The log goes to `~/.wunderland/log.txt`, settings to the registry (`HKCU\Software\WunderWungiel\Wunderland`).
- `HSWidgetxWunderland*.dll` are prebuilt homescreen-widget publisher binaries; they are not built from this repo. The `DEPLOYMENT` rules in the `.pro` package `C:\HSWidgetxWunderland_E9320736_rel.dll` and `C:\Wunderland.png` from the drive root, so both must exist there or `make sis` fails.
- Debug output (`qDebug`/`qWarning`) goes through `Logger` (`logger.*`, ported from Symbisend) to `download/Wunderland/log.txt` on F:, E: or C:/Data (truncated on each start).
- `#xqinstaller*` sources are intentionally commented out of `SOURCES`/`HEADERS`.

## Architecture

- **All Symbian APIs and Qt Mobility calls live in `platform/`**, each with a desktop fallback under `#ifdef Q_OS_SYMBIAN` (Mobility and `qt-components` are only in `CONFIG` on Symbian). Code outside `platform/` must be pure Qt. Include these headers as `"platform/apps.h"` etc., not via `INCLUDEPATH` (the SDK has its own `platform/mw/hswidget.h`). `platform/apps.*` (`namespace Platform`): SIS registry and AppArc (installed version, installed, launch, visible apps, open installer, open URL in the default browser), with leaving calls in trapped `…L()` helpers. `platform/device.*`: OS version, device language, download folder. Also `installerwatcher.*`, `subscriber.*`, and `hswidget.*`/`qhswidget.h` (Symbian-only, not built on desktop).

- `main.cpp` owns the one `QNetworkAccessManager` and the `StoreApi` built on it, and constructs the C++ backend singletons and exposes them to QML as context properties: `appCatalog`, `installManager`, `updateTracker`, `appManagement`, `news`, `update`, `l` (Language), `subscriber`, `settings`, `symbianFunctions`, `logger`, plus `launchAppId` (parsed from an `appListId:<n>` launch argument). `docs/qml-api.md` documents everything QML can use (properties, roles, invokables, signals, error codes); update it when that API changes. On Symbian it also creates the homescreen widget (`HSWidget`, `platform/hswidget.*`) and registers it 1 s after the UI is shown (registering is slow and used to delay the splash screen). The backend objects get their dependencies as constructor pointers (one `AppManagement`, one `UpdateTracker`) and are connected in `main.cpp`.
- QML entry point is `qrc:/qml/Wunderland/MainAppLoader.qml` → `main.qml` (PageStackWindow; pages pushed as `pageStack.push(Qt.resolvedUrl("X.qml"), {...})`; `PageStack` loads the URL and throws with the load error, while an unchecked `Qt.createComponent` would hide it). **All QML, images and `.qm` files are loaded from `Qml.qrc`, not from disk** (`DEPLOYMENTFOLDERS` is disabled) — any new QML/image/translation file must be added to `Qml.qrc`.
- `StoreApi` (`storeapi.*`) is the only way to talk to the server: base URL (default `http://ovi.wunderwungiel.pl`, overridable via the `network/baseUrl` setting), `buildUrl()` adding the common `os`/`resolution`/`language` parameters, `get()` returning an `ApiReply` that follows redirects, times out after 30 s without data, checks errors/HTTP status, emits `finished()` once and deletes itself. Errors are `StoreApi::Error` codes. `download()` is the same but streams the body into a `QIODevice` (used by `Downloader`, which saves to `download/Wunderland` on F:, E: or C:/Data). `AppCatalog`, `UpdateTracker`, `InstallManager`, `News`, `Update` and `Downloader` take a `StoreApi*`.
- `AppCatalog` (`appcatalog.*`) owns the app lists: it fetches them from `applist.php` (latest / category / search / personal / updates), parses the XML response with `AppListParser` (`applistparser.*`, `QXmlStreamReader`; also used by `UpdateTracker`, `News` and `Update`) into `AppEntry`s, lets `UpdateTracker::track()` set each app's install/update state, and appends them to five `AppListModel`s (`applistmodel.*`, a `QAbstractListModel` over `QList<AppEntry>`; QML reads a row with `get(row)`). `appentry.h` holds the `AppEntry` struct, the `AppRole` enum and `appRoleNames()` (the names QML reads); use the enum, never `Qt::UserRole + N` literals, and keep the role numbers stable.
- `InstallManager` (`installmanager.*`) is the download → installer → result flow for one app at a time: it owns the `Downloader` and the `InstallerWatcher` (`platform/installerwatcher.*`; `RThread::Logon` on the installer thread from `StartDocument`, falling back to a UI-thread poll for the `installserver` process), exposes `state`/`progress`, decides the detail page button (`buttonAction`/`buttonPressed`, `InstallManager::Action` enum, registered as an uncreatable QML type in `Wunderland 1.0`), and emits `appInstalled(id)`, which `main.cpp` connects to `AppCatalog::markInstalled`.
- `AppManagement` detects installed apps through `platform/apps.*` (SIS registry, `-lsisregistryclient`); `hasUpdate(uid, version)` (or `isNewer(installedVersion, version)` when the installed version is already read) is the one update check (used by `UpdateTracker` and `InstallManager`). Version comparison (`compareVersions`, `isNewer`) lives in `versioncompare.*`. `installedStoreIds()` maps installed UIDs to store IDs using the bundled `apps.txt` (no persistence).
- `UpdateTracker` (`updatetracker.*`) is the only owner of the persisted app state: `apps/installedIds`, `apps/updateIds`, `apps/highestSeenId` (in memory, written through to QSettings), `settings/appsScanned` and `widget/lastUpdateTime` (key strings only in `updatetracker.cpp`, keeping the old keys). It, exposes the update `count`, and runs the update check of installed apps (`check()`; at startup from `main.cpp`, and from `HSWidget` when the last check is a day old). It is shared by `AppCatalog`, `InstallManager` and `HSWidget`; don't read or write those keys elsewhere. On the first run its constructor adds the installed apps known from `apps.txt` (`AppManagement::installedStoreIds()`) to the installed list. `Update` checks for a new version of Wunderland itself (`version.xml` / `changelog.xml` on the server). `News` reads `feed.xml` into a `NewsModel` (`newsmodel.*`) and loads the linked pages as HTML for the in-app `WebView`.
- Only the default (self-signed) variant of an app is supported; the AppList unsigned/Store variants (`uidstore`, `versionunsigned`, ...) were removed. Their old `Qt::UserRole` numbers are left as gaps. The `installed` role is a `bool`; use the `uid` role for the app UID.
- Persistent state uses `QSettings` with no arguments: `main.cpp` sets the organization (`WunderWungiel`) and application (`Wunderland`) name first, so the storage location is unchanged. User options are `Q_PROPERTY`s of `Settings` (`settings.*`: `darkTheme`, `aasFeed`, `newsOpenInBrowser`; key strings only in `settings.cpp`, keeping the old keys); QML reads and assigns them directly (`settings.darkTheme = checked`). Other keys: `settings/languages` (`Language`), `network/baseUrl` (`StoreApi`), `apps/*`, `settings/appsScanned`, `widget/lastUpdateTime` (`UpdateTracker`).
- `resources/*.xml` are sample/template server files, not used at runtime.

## Translations

- `.ts` sources and compiled `.qm` files are both committed at the repo root; `wunderland_template.ts` is the base for new languages.
- Adding a language requires: the `.ts`/`.qm` pair, an entry in `TRANSLATIONS` in `Wunderland.pro`, the `.qm` in `Qml.qrc`, and the language code (alphabetical) in `_languageCodes` in `language.cpp` (with its display name in `_allLanguages` at the same index). The UI translator is loaded from `:/wunderland_<code>` based on the device language.
- Category names are translated in `Language::initCategories()`; their order defines category IDs (head categories are 0, 12, 19).

## Commits

Don't put refactoring-plan step numbers (e.g. "plan 2.1") in commit titles. Describe the change itself.

## Version bumps

The version is hardcoded in three places that must be updated together: `VERSION` in `Wunderland.pro` (e.g. `2.0.5`), and the display strings in `qml/Wunderland/AboutPage.qml` and `qml/Wunderland/SplashScreen.qml` (e.g. `2.00(5)`).
